## 1. 结论

持续 404 的直接原因，是英语 App 联调假服务占用了 WB 主池的 **8790** 端口。8788 入口仍活着，继续把主池份额转给提供 `/rewrite/*` 等联调接口的 Python 服务。辅池 8789 仍能成功响应，因而表现为部分调用成功、部分调用失败，主池面板与状态接口也受到影响。

原始 DSH 父会话记录了具体操作链：**把 8790 的两个监听 PID 当成“重复 stub”强制结束，再启动假服务；已检查的原始记录中未见先核对它们可执行路径和命令行的证据。** 主池最后一次 200 与强杀命令仅相隔 7 毫秒；重启假服务后紧接着出现持续 404。

两个被杀 PID 的实际进程身份没有留在已检查的原始记录中，不能把它们都认作 Python，也不能指定其中某一个必然是 WB。现有证据不支持将这次故障直接归因于额度耗尽、账号全挂或 WB 程序自身 panic。

本轮在 **11:10:57** 恢复主池：7/7 账号健康；辅池原进程保留。后续线上验证只发送 GET，没有调用真实模型来测试。

## 3. 为什么没有自愈

1. 原主启动器只查 8790 是否监听。错误服务占用后，启动器直接成功退出。
2. 原全局守护只覆盖 8788/8789，而且把“有监听者”当成存活，没有验证服务身份。
3. 原入口只查辅池健康。主池错误时，离线调度仍给主池 5:3 权重中的主池份额。权重不是实测总失败率。
4. 原路由存在辅转主的错误重试分支，可能使故障时的请求处理难以判断。
