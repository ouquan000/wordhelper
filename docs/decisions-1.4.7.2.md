## 2. 用户已经确定的要求

### 2.1 思路质量

1. 用户通常留空点击重写，期待系统主动找出更好记的路线。
2. 重写要记住这个词此前的抱怨和失败路线。空白重写默认换路线，用户主动修改要求时按新要求处理。
3. 必须从英文拼写或读音唤起画面，再由画面连到词义。拼写、读音与熟词的自然联系均可使用。
4. 适合的词允许以词根为主方法，前提是解释清楚并建立记忆联系。某词已经被用户否定的路线需要避开。
5. 以用户已有点赞作为正样本，以点踩、重写抱怨和后续否定作为负样本。保留原文、版本、词书和评价时间。
6. 保留旧点赞版本。检查发现的疑点形成清单，自动修订重点放在点踩版本及确认不合格的其他卡。
7. 同词有过点赞、后来又点踩时，需要按具体正文与时间区分，避免把旧认可误当成当前认可。

### 2.2 持续重写与学习流程

1. 稿件质量不合格时继续自动处理，没有固定总尝试次数。
2. 失败后间隔重试，其他词照常处理，提供随时停止入口。
3. 合格后再放回学习队列，可以晚一些。
4. 当天其他词背完后停在等待页，合格一个就能继续背一个，用户自行决定何时退出。
5. 点击重写后，在现有“认识”按钮右侧显示“跳过”。保留“认识”的名称。
6. 跳过按钮在本次停留于该词期间保持显示，生成完成也保持位置，换词后收起。

### 2.3 连接与版本范围

1. 同一 WiFi 下自动优先连接同一台电脑的局域网地址，局域网失败或换网后走域名。
2. 用户无需手工切换地址，自动切换必须确认服务身份与配对关系。
3. 本版包含前轮清单中的全部遗留项，按模块分阶段实施和验收。
4. 全词包检查之后，针对确认有问题的卡批量重写。
5. 工作用模型为 WB 反代 DeepSeek V4.1 Flash，推理强度 max。DSH 模型标识为 `wb-proxy/deepseek-v4.1-flash`。
6. WB 的稳定性是明确约束，需要控制本项目工作负载。

## 3. 实施分组与完成条件

### W1 反馈、质量与个人偏好

主要文件包括 `RewriteRepository.kt`、反馈实体与 DAO、`tools/rewrite-service/store.py`、`pipeline.py` 及现有 prompts。

- 修复反馈上传版本号，验证本地保存、上传、服务端记录和版本关联。
- 对历史反馈建立可追溯视图，按词书、单词、正文指纹、反馈 ID 和时间关联。版本号冲突保留原始记录与不确定性。
- 识别并隔离测试与无效记录。原始反馈采用保留和旁路派生方式，便于回查。
- 建立同词失败路线与原话历史，保留完整事件，进入提示词的上下文使用有依据的摘要。
- 用户的新明确要求优先于旧要求。摘要更新保留来源，处理跨轮意见冲突。
- 个人偏好从有效点赞和点踩抽取，使用正负样例。生成与润色接收偏好，独立评委依据明确质量标准判断。
- 把英文线索到画面、画面到核心词义的联系纳入质量检查，逐段指出断点，防止靠堆字数和高分掩盖问题。
- 修订两段式评分规则，给拆分成立、自然联系、词义正确、用户约束设置硬性条件，写清可放宽的文风维度。
- 给未使用谐音等“不适用”维度定义确定语义。
- 评委的 intent、same_method 与维度字段做严格解析。缺关键字段、未知维度、模糊别名冲突进入补判或延后处理。
- 末行禁令例外与用户明确许可关联，覆盖无许可、许可仅尾注、单行、多行和否定式提及。
- 原因、分数、轮次与展示稿件对应，避免用最后一轮问题解释另一轮成品。

验收覆盖 `obscure` 的既有完整反馈链，以及正样本中多种记忆方法。空白重写仍继承已确认的原话约束，过期路线得到识别，用户的新要求能解除旧约束。历史反馈关联的准确率与存疑清单单独报告。

### W2 持久化持续重写与队列公平

主要文件包括 `service.py`、`store.py`、`pipeline.py`、`RewriteQueueItem`、`RewriteRepository`、`LearningViewModel`。

- 将有限单轮流水线与可持续调度分开。一次调度只做有界工作，质量未通过的任务持久化下次可运行时间和失败摘要。
- 质量未通过时保留待处理状态与当前可用正文，合格结果再应用并插回。
- 区分质量不合格、模型响应格式错误、传输故障、限流和额度耗尽，分别记录和调度。
- 任务轮换公平，前台用户任务优先于离线批量任务。同词重复点击合并或更新，旧任务结果按代次校验。
- 停止动作同时处理待运行、运行中、晚到结果和重启后的状态，停止后旧结果依照任务代次守卫处理。
- 队列、失败次数、冷却时间、取消状态、插回意图、历史摘要在重启后可恢复。
- 保留按书隔离，回插与当天完成判定共同覆盖，验证多个词陆续完成时逐个继续学习。
- 撤销同时恢复正文、方法和该版本复核状态，处理更早数据缺少状态的兼容语义。
- 新策略下对旧 unverified 记录给出兼容展示和后续处理规则。

验收包括连续质量失败、失败后公平轮换、冷启动、电脑进程重启、重复上传、运行中更新要求、停止后晚到结果、跨书任务及全部待处理时的等待页。

## 4. WB 负载与调度约束

1. DSH 指定 `wb-proxy/deepseek-v4.1-flash`，推理强度 max。App 对应型号以现有 `ds-v41-flash` 映射核验。
2. 本项目的重模型工作初始采用串行安排。DSH 实现、真实模型测试和批量词包任务分阶段运行，前台重写优先。
3. 当前 App 服务有两个 worker，实施时需把本项目模型调用的实际总并发纳入统一约束，覆盖运行中的两个 worker 和离线任务。
4. 为 HTTP 429、Retry-After、模型额度耗尽、503 model_busy、传输中断与格式错误建立不同处理路径。网关异常触发项目级冷却，恢复后有界探测和逐步恢复。
5. 禁止多层短间隔重试相乘，禁止为加速批量工作增加网关实例或重新启用暂停的辅池。
6. 持续质量重写与网关冷却共同工作。任务保留，冷却期间让出 worker 和执行槽。
7. 本轮保持 WB 正式配置、路由、实例与账号状态。额外网关修复若被证据证明必要，另列最小变更与影响。
8. 先验证一小批实际调用的完成、重试和负载，再扩大离线批次。每批可停止、可续跑、可追踪。

## 5. 建议实施顺序

1. P0 只读审查，补齐当前配置与根因证据，校对所有既有报告的修复状态。
2. P1 反馈版本关联与质量标准，形成真实正负样本和历史约束视图。
3. P2 持续队列、停止与恢复、跳过和等待页，优先打通用户连续背词的主流程。
4. P3 连接身份、局域网优先、服务健康和数据恢复，迁移集中设计和验证。
5. P4 动效、冷启动与确定性词包检查，候选修订先小批测量再逐批处理。
6. P5 集成测试、独立测试审查和独立产品验收、电脑重启与网络矩阵、24 小时长跑。
7. P6 汇总结果、已知边界、回退步骤与发布候选。装真机与正式发布安排在交付确认后。

各组独立回滚，Android 共享文件与构建安排串行集成。首次全词包语义扫描及定向修订可能是长时任务，以实际小批数据估算工期。
