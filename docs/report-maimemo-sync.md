# 墨墨背单词 · 同步机制调研报告

> 调研日期：2026-11-06
> 方法：官方文档 + 开放 API 文档 + 算法公开论文页 + 第三方实现交叉验证
> 结论可信度分三级：**官方文档** / **可复核的第三方实现** / **推断**

---

## 结论先行

墨墨的同步**不是** Anki 那种「增量合并」，而是**服务端权威 + 整包上传/下载**：

- 学习状态（每个词什么时候再复习、上次答得怎么样）**只有服务端一份权威数据**，客户端是显示器；
- 客户端之间不合并，靠用户「A 上传 → B 下载」保证谁是新的；
- 排程算法（MM / MMX）在服务端算，客户端拿到的是 `next_study_date` 这种已经算好的结果。

这解释了一个反直觉的现象：**它敢让用户手动上传/下载，是因为它根本不担心合并**。

## 一、官方怎么说

### 1.1 换设备与重装：明确是「整包上传 / 整包下载」

官方 FAQ《更换学习设备时，如何将学习数据从 A 设备同步到 B 设备？》原文：

> **同步数据含两种操作：上传数据 / 下载数据**
> 更换学习设备：先在 A 设备上传学习数据（我的 - 学习数据同步 - 上传），后在 B 设备下载学习数据
> 卸载重装：在当前设备【上传学习数据】后，再进行卸载重装

来源：<http://memodocs.maimemo.com/docs/TJDKwbRRfi1prCktSXPcDQjrnJf>（**官方文档**）

同一页还有一条关键警告：

> 开启自动同步前，务必确保要开启同步的设备保存着【最新学习数据】

**这条是「没有自动合并」的直接证据**——如果服务端能做冲突合并，就不需要用户先保证「我这台是最新的」。

### 1.2 自动同步是一个开关，不是一个协议

路径：`我的 - 学习数据同步 - 学习数据自动同步`，开关式（同上，**官方文档**）。

触发点不是「实时」，而是 **App 退到后台**。官方网页版 FAQ 原文（**官方文档**）：「在 App 中完成学习后，需要将 App 退出到后台，才会触发自动同步」「同步完成后，网页版才能获取最新的学习进度」。

### 1.3 开放 API 反证：学习数据由服务端算好再下发

开放平台学习接口文档开头写着（**官方文档**，`memo-api/references/study-api.md`）：

> **Beta（公测）**：限时试用，不保证可用性，可能随时调整。**需要打开自动同步**。如果当日未打开 App 进行初始化则无法准确计算。

「当日没打开 App 就算不准」意味着：**服务端的排程依赖客户端上报的当日行为**，而不是两端各自算完再对账。

### 1.4 它压根不支持完整离线学习

官方 FAQ《墨墨支持离线学习吗？》原文（**官方文档**）：

> 墨墨目前仅支持个别功能离线使用，所有与网络相关的功能（如同步数据、获取新词等）均需联网才能操作，建议你连接网络后再进行学习。

这条把整包模型的前提补齐了：**客户端不会长时间离线攒下一堆本地改动**，所以服务端永远是最新的那一份，不需要合并。

## 二、从数据模型反推它的同步设计

开放 API 返回的 `StudyRecord`（**官方文档**）：

| 字段 | 含义 |
| --- | --- |
| `add_date` | 加入计划的时间 |
| `first_study_date` | 首次学习时间 |
| `last_study_date` | 最近一次学习时间 |
| `next_study_date` | 下次复习时间（**服务端算好的结果**） |
| `last_response` | 最近一次作答 |
| `study_count` | 学习次数（**每天最多计 1 次**） |
| `tags` | `STICKING`（老忘）/ `WELL_FAMILIAR`（熟知） |

作答枚举 `StudyResponse`：`FAMILIAR` 认识 / `VAGUE` 模糊 / `FORGET` 忘记 / `WELL_FAMILIAR` 熟知 / `CANCEL_WELL_FAMILIAR` 取消熟知。

**这张表里没有任何同步元数据**：

- 没有 `updated_at` / `mod_time`
- 没有 `revision` / `usn` / 版本号
- 没有操作日志（每次复习一条记录）——`study_count` 一天最多 1 次，等于**每天只留一个状态快照**

也就是说：**服务端保存的是「每个词当前是什么状态」，不是「这个状态怎么变来的」**。没有历史，就没有可合并的东西；没有可合并的东西，同步就只能是整包覆盖。这是设计上的必然，不是偷懒。

> 对照：Anki 的每条 note/card/revlog 都带 `usn`（本地改动 = -1），删除进 `graves` 墓碑表，冲突比 `modTime`，复习历史只追加——**正是因为允许两台设备离线各改各的**。墨墨不需要这套，因为状态只有一个写者（云）。

### 用户自己写的内容才有对象级 CRUD

释义 / 助记 / 例句这三类是用户创建的资源，它们的 schema 带 `created_time` / `updated_time` 和 `status`（`PUBLISHED` / `DELETED`）：

- 助记 `notes`：`note_type` 有 21 种取值（联想 / 谐音 / 派生 / 词根 / 词源 / 固搭 / 语法 / 对比 / 近义 / 反义 / 扩展 / 串记 / 口诀 / 合成 / 吐槽 / 其他 / 固定搭配 / 词根词缀 / 辨析 / 近反义词 / 图例）
- 释义 `interpretations`：多标签（简明 / 详细 / 英英 / 四级 / 六级 / 考研…，最多 3 个）
- 例句 `phrases`：句子 + 译文 + 标签 + `highlight`（单词在句中的字符区间）+ `origin`

`DELETED` 是软删（相当于墓碑），但**只在用户内容这一层**，学习状态层没有。

## 三、换设备到底发生了什么

结合 FAQ 与 API：

1. A 设备点「上传」→ 把本地这份**学习状态整包**推到服务端；
2. B 设备点「下载」→ 从服务端拉回**同一份整包**，覆盖本地；
3. 之后 B 设备学习，改动再推回服务端；
4. 自动同步开启时，App 每次**退到后台** flush 一次整包推送，但**仍是「推/拉整包」，不是「对账合并」**。

推论（**推断**）：服务端对同一账号是单写者模型——最后一次上传覆盖之前的状态。这也解释了为什么 FAQ 要求「开同步前先确认这台是最新的」。

## 四、和我们的项目对照

我们自己的 App（不爱背单词 1.3 改造版）：

| 维度 | 墨墨 | Anki | 我们 |
| --- | --- | --- | --- |
| 学习状态存储 | 服务端权威，整包 | 本地 + 增量合并 | 本地 SQLite，每词一行 |
| 每个词的字段 | 加入/首次/最近/下次 + 最近作答 + 次数 | 大量调度参数 + 完整 revlog | 16 列 SM-2 参数 + 最近时间 |
| 逐次复习日志 | 无（一天一条状态） | 有（revlog） | 无 |
| 冲突合并 | 不做（整包覆盖） | usn + modTime + graves | 不适用（单端） |
| 排程算法在哪 | 云端 | 本地 | 本地 |

**关键结论：我们的 `tb_progress` 与墨墨的 `StudyRecord` 是同构的**（都是「每词一行的当前状态」，都没有历史）。所以我们天然适合墨墨式方案，而不适合 Anki 式方案。

## 五、能抄什么，不能抄什么

### 能抄

1. **内容与状态分离**。墨墨的助记/释义/例句（内容）和学习记录（状态）是两套结构、两套接口。我们的 `tb_word_memory`（内容）和 `tb_progress`（状态）正好也是两套——内容可以随时整体替换，状态完全不动。
2. **单写者原则**。状态只让手机写，电脑只读。这样永远不会冲突，不需要 usn、不需要墓碑、不需要合并器。
3. **软删 + 时间戳**。用户内容这一层用 `status` + `updated_time` 就够，我们是单端，连软删都可以省。
4. **「谁是新的」由用户/程序显式保证**，而不是让系统猜。墨墨让用户确认，我们让电脑端维护一个 `contentVersion` 就够。

### 不能抄 / 不必抄

1. **服务端权威排程**。我们不需要账号体系，手机本地算 SM-2 已经跑通了。
2. **整包上传/下载学习数据**。我们的状态只在一台手机上，没有第二台设备要同步。
3. **多端自动同步**。一旦要做，就得回答「冲突怎么办」——而我们的答案是「不做多端」，所以这个问题不存在。

## 六、对我们「电脑 → 手机」这条路的具体启示

我们真正要的通路只有一条：**电脑生成内容 → 手机接收**。这条通路**根本不碰学习状态**，所以：

- 不需要同步协议，只需要「导入 + 版本校验」；
- 冲突面为零（内容表按 `word_id` 整体替换，进度表一列不动）；
- 失败可以整包回滚（旧内容还在，只是没被替换）。

这和墨墨「上传/下载整包」在工程上是同一类操作，但比它更简单——因为我们只有单向、单写者、无账号。

## 九、交叉复核补充（子智能体独立取证）

1. **触发时机比「开关」更具体**：App 退到后台才推一次整包（官方网页版 FAQ，原文见 1.2）。
2. **云端保留多条历史上传快照**：`我的 → 学习数据同步 → 查看历史上传数据` 可按时间段重新下载（**官方论坛·官方账号**，但那是姊妹产品「墨墨记忆卡」侧；背单词侧同名入口未在文档中找到明说 → 中等可信）。
3. **覆盖不会自动发生**：B 上传不改写 A 本地，A 不点「下载」就不受影响 → 冲突退化成「用户选了哪份数据」。
4. **开放 API 没有「提交复习反馈」的端点**：只能 `add_words` / `advance_study` 改计划 → 复习的**写路径完全不开放**，第三方做不出真正的第三方背单词客户端。
5. 状态变更的最小单位是 **(单词 × 天)** 的幂等单元格：`study_count` 注释 `max 1/day`，`first_response` 仅当天首次 → 重复提交天然可忽略。这是它敢整包覆盖的底层原因。
6. 内部**确实存在逐次复习日志**（术语页「认知过程历史记录」= 每次反馈 + 间隔 + 回忆耗时），但开放 API 不暴露，推测只服务算法训练。
7. 导出只有 PDF，且渲染在客户端本地（优先取本地缓存内容），没有 CSV / JSON 结构化导出。
8. **内部 App↔服务端协议没有公开证据**（无抓包、无逆向、无仿冒客户端）。本报告所有结论只到「整包上传 / 下载」这一层，不推测协议形态。
9. 算法：官方明说 MMDB / FVI / WDR / MRL 是**全局训练、迭代发版**的查表模型，MM-4 按用户记忆能力分配不同 MMDB → 分档在云端；但官方**从未明说**「算法运行在服务端」，属**推断（证据强）**。
